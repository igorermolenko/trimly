### R1 — [stage-1] A bare `https://` or `http://` gets the AC-05 encoding answer instead of AC-03 — **Fix now**

- **Where:** `src/main/java/io/github/igorermolenko/trimly/link/domain/TargetUrl.java:48`, `:58-61`.
- **AC / contract:** AC-03 (an address that is not an absolute web address with a host), AC-05.
- **Problem:** `looksLikeWeb` checks only the scheme prefix. `new URI("https://")` throws "Expected authority", so since T39 both `https://` and `http://` give `link.target_url_not_encoded`. Before T39 they gave `UNSUPPORTED`. An unclosed IPv6 host such as `https://[::1` gets the same wrong answer. The round-4 Q2 resolution asked for both scheme and host to be decided before the strict parse; only the scheme is. This is a regression from 159d6d4.
- **Raised by:** fix-verification reviewer. The dispatcher reproduced it by reading `TargetUrl.java:41-61` against the pre-T39 version.
- **Resolution:** Fix now. In the `catch`, return `NOT_ENCODED` only when the text after `scheme://` has a non-empty authority (at least one character before the first `/`, `?` or `#`); otherwise return `UNSUPPORTED`. Add `https://` and `http://` to the `UNSUPPORTED` cases in `TargetUrlTest`.

### R2 — [stage-1, docs] The firewall-rejected 400 is documented only on create — **Fix now**

### R3 — [stage-1, low] Tomcat answers invalid percent-escapes with its own HTML 400, so these addresses never get "Link not found." — **Fix now**

- **Where:** `src/main/resources/application.yml:51-57` (the comment at `:51-54` says that everything still rejected reaches `VisitorRequestRejectedHandler`, which is not true); `redirect/api/VisitorErrorController.java:25-28`; test gap at `RedirectIT.java:119-134`.
- **AC / contract:** AC-16b; openapi `/{shortCode}` 404.
- **Problem:** Tomcat rejects `GET /abc%zz`, `/abc%` (a browser sends a typed lone `%` as is), `/abc%2`, `/abc%00`, `/abc%5C` and `/%2e%2e/x` while it decodes or normalises the URI. This happens before any filter runs and before the `/error` dispatch. The answer is 400 `text/html` "HTTP Status 400 – Bad Request" without `no-store`. Under `/api/...` the same requests get a 400 with no Problem `code`. The reviewer confirmed this with a standalone embedded-Tomcat 11.0.27 probe that used the app's slash and relaxed-character settings. This is the same layer as round-4 Q1, which covered only raw characters.
- **Raised by:** trace reviewer.
- **Resolution:** Fix now. Install a custom Tomcat `ErrorReportValve` through a `WebServerFactoryCustomizer`. For a 400 raised by the server itself, it writes 404 `text/plain` "Link not found." with `no-store` outside `/api`, and a `shared.malformed_request` Problem under `/api`. Add raw-socket `RedirectIT` cases (`/abc%zz` and `/abc%` → 404 text with `no-store` and no lookup) and an `/api` case. Correct the yml comment.

### R4 — [stage-1, low] Startup validation accepts a public base URL with a path or query, so every short link built from it is dead — **Fix now**

- **Where:** `src/main/java/io/github/igorermolenko/trimly/link/app/LinkProperties.java:20-26`.
- **AC / contract:** AC-01, AC-08; sad.md §8 Configuration ("validated at startup, failing fast").
- **Problem:** `TRIMLY_PUBLIC_BASE_URL=https://trimly.example.test/s` passes the check. Create then answers with `https://trimly.example.test/s/aB3dEf9`, a two-segment path that `RedirectController.java:45-49` answers with "Link not found." With `https://trimly.example.test?x=1` the short link becomes `…?x=1/aB3dEf9`.
- **Raised by:** trace reviewer.
- **Resolution:** Fix now. Also require an empty path and no query, fragment or userinfo. Optionally, refuse `own-hosts` entries that are not bare host names (for example `https://x.test`, which can never match). Add these cases to `LinkPropertiesTest`.
